# セッション引き継ぎの置き場と確認先（このリポジトリ）

> **手順の正本はグローバルスキル [[session-handoff]]。**
> 2つのモード（直列＝段階1〜5／分岐と合流＝段階F0〜F5）、引き継ぎを決定と同じファイルに
> 置かない理由、開始キーワードを文書へ書かない理由、分流プロンプトが持つ5点、
> 分流が戻る前に自分へ掛ける検問、各テンプレートは、すべてそちらが持つ。**ここへ複製しない。**
> 本スキルはこのリポジトリ固有の**置き場の実値**と**確認先**だけを持つ。

## 変数の実値

グローバル側が `H` / `S` / `B` / `M` と呼ぶ4つは、このリポジトリでは次を指す。
**置き場の規約そのものの正本は `docs/DOCUMENT-RULES.md`** であり、本表はその索引である。

| 変数 | このリポジトリでの実値 | 規約の正本 |
|---|---|---|
| **H: 引き継ぎファイル** | `plans/HANDOFF-<topic>.md`（**`docs/` ではない**。上書き運用） | `docs/DOCUMENT-RULES.md`「セッション引き継ぎは`plans/HANDOFF-<topic>.md`に置く」節 |
| **S: 状態の正本** | `docs/STATUS.md`（残課題はここ一箇所） | 同節・不変条件4 |
| **B: 欠陥の記録先** | `docs/bugs/BUG-NNN.md` ＋ `docs/bugs/BUG_CATALOG.md` へ1行追記 | [[bug-catalog-rules]]（このリポジトリのスキル） |
| **M: 合流先** | `plans/HANDOFF-<topic>/`（**同名の `H` と対になるディレクトリ**） | `docs/DOCUMENT-RULES.md`「分岐した調査の合流先」節 |

- **`H` は既に複数本が運用中である。** 新しい topic を切る前に `plans/HANDOFF-*.md` を一覧し、
  既存のものへ上書きすべきでないかを見る——同じ調査に2本目を作ると、どちらが現在か読めなくなる
- **`M` が `plans/HANDOFF-<topic>/` なのは、本流の `H` と名前で対にするため。**
  `plans/HANDOFF-MAC-ARGV.md` から分岐したなら `plans/HANDOFF-MAC-ARGV/` である。
  親子が名前だけで辿れるので、`INDEX.md` の「親」欄と食い違ったときに気付ける
- `S` からは `H` へリンクを置く（`docs/STATUS.md` が各論の入口になる）

## 引き継ぎ文で名指しする番号体系

次のセッションは文脈を持たないので、**番号だけで書かず、初出でひと言展開する**
（`CLAUDE.md`の説明規約。詳しくは `premise-first-explanation`）。

| 記号 | 何か | 正本 |
|---|---|---|
| `M00`〜`M20` | 実装フェーズ | `docs/INDEX.md` |
| `Tier0`〜`Tier3` | シェル隔離の段階 | `plans/DESIGN-SANDBOX.md` |
| `D-NN` | 拘束的設計決定 | 各 `plans/DESIGN*.md` の「拘束的設計決定」節 |
| `P-NN` | セキュリティ上位原則 | `docs/SECURITY-PRINCIPLES.md` |
| `B-NN` | バグ由来の実装規律 | グローバルスキル [[bug-pattern-rules]] |
| `BUG-NNN` | このリポジトリのバグ | `docs/bugs/BUG_CATALOG.md` |

**開始キーワードで最初に読ませる文書**は、たいてい `docs/STATUS.md`（今どこまで出来ているか）と
`plans/HANDOFF-<topic>.md`（次の一手）の2つで足りる。設計の根拠まで要るときだけ
`plans/DESIGN*.md` の節を1つ足す（3件を超えたら、それは引き継ぎではなく再説明である）。

## 段階3（マシンに残した副作用）の確認先

グローバル側は一般論（ETWセッション・ACE・共有・サービス）までしか書けない。
このリポジトリでは実マシンに残るものが多いので、次を見る。

| 残り得るもの | 扱い |
|---|---|
| **`%APPDATA%\harness\config\` の台帳群** | **消してはいけない。** どれが恒久的な穴になり、どれが自己修復するかは `docs/DEV-ENVIRONMENT.md`「クリーンアップ時に絶対に消してはいけないファイル」が正本。膨らんだら手編集せず `harness fs prune`（下見は `--dry-run`） |
| **loopback exemption**（マシン全体で1本のリスト） | 所有者台帳は `%ProgramData%` 側。残留は次のTier2aセッションが引き取るが、**実行中の別セッションがあると参照カウントが割れる**。同上の節が正本 |
| **常駐・昇格プロセス** | `harness-netfilterd` / `harness-privhelper` / `harness-vmsandboxd` / `harness-policy-learnd`。**記憶で書かず実測する** |
| **ETWセッション** | `logman query -ets`。ポリシー定義モード（`--policy-learn`）を回した後に残り得る |
| **AppContainerプロファイル・付与したACE** | セッション単位プロファイル（D-37）。台帳で追跡されているので、**台帳を消さないことが撤収可能性そのもの** |
| **Tier3のVM・Incusコンテナ** | 台帳で追跡。孤児VMは台帳が消えると追えなくなる |

### 確認コマンドで昇格が起きるなら、それも `dev-elevated-runner` 経由

**条件は「テストか」ではなく「昇格が起きるか」である**（`CLAUDE.md`の規約）。
残骸を確認するだけのつもりの単発コマンド（`CheckNetIsolation` 等）でも、昇格するなら対象になる。
`dev-elevated-runner` は `KNOWN_TARGETS` との完全一致しか通さないので、**その操作の側をテストにして
`KNOWN_TARGETS` へ足す**。PreToolUseフックが素の `sudo` を機械的に止めるので、
**フックが `ask` を返したら押し切らずに規約へ戻ること**。

**引き継ぎ文には「確認した」と「まだ残っている」を書き分ける。**
`docs/DEV-ENVIRONMENT.md` の手順を通したのかどうかまで書かないと、次のセッションは
確認済みだと思って先へ進むか、確かめ直して時間を使うかのどちらかになる。

## このスキルの育て方

このリポジトリで引き継ぎがうまくいかなかったとき（次のセッションが台帳の残骸で混乱した・
`H` を2本作ってしまった・分流が `M` の外へ書いた）、**置き場と確認先の話なら**ここへ1行足す。
**手順の話ならグローバル側**（[[session-handoff]]）へ足す——どちらか迷ったら、
「他のリポジトリでも同じことが言えるか」で決める。言えるなら手順である。
