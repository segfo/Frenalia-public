# バグカタログの固有値（このリポジトリ）

> **書式の正本はグローバルスキル [[bug-catalog-rules]]。**
> ID規約・標準セクション構成（症状→図解→原因→修正→設計メモ→教訓→参照）・
> 執筆原則・原因究明の観点・記録手順チェックリスト・良い見出しの例は、すべてそちらが持つ。
> **ここへ複製しない。** 本スキルはこのリポジトリ固有の**値と配置**だけを持つ。
>
> グローバル側§2が「実際の深さはリポジトリの構成で決まるので、そのリポジトリのスキル／
> 文書規約が対応表を持つ」と明示的に委譲しているのが、下の相対リンク表である。

## 置き場

```
docs/bugs/
├── BUG_CATALOG.md          ← 一覧インデックス（必ず1行追記する）
├── BUG-NNN.md              ← 個別バグ
└── images/
    └── bug-NNN-xxx.svg     ← そのバグの図解（任意）
```

**ID はこのリポジトリの中でしか一意でない。** OS自作リポジトリのカタログとは低い番号帯が
全件衝突している。**他リポジトリのバグを引くときは必ずリポジトリ名を添える。**

**件数をどこにも書き写さない。** 実数は `docs/bugs/BUG-NNN.md` を数えれば出る——
写した数字は必ず片方だけ古くなる（このリポジトリでは「消してはいけない台帳の件数」が
実際にずれている）。

## フェーズ表記

**発生・発覚したフェーズを、番号＋括弧で内容**を添えて書く。このリポジトリで使う軸は3つある。

| 軸 | 書き方の例 | 正本 |
|---|---|---|
| 実装フェーズ | `M07（リッチTUI）`／`M12補遺（Tier1a fs passthrough D-13）` | `docs/INDEX.md` |
| 隔離Tier | `Tier3 Phase B（VM共有化）実機E2E中に発覚` | `plans/DESIGN-SANDBOX.md` |
| 拘束的決定 | `Tier2a・D-54（workspace capability）` | 各 `plans/DESIGN*.md` |

**発覚の文脈まで書くのが本リポジトリの慣行である**（「〜の実機E2E中に発覚」「〜の修正コードが
原因」）。どの作業をしていて踏んだかが、同型の穴を探すときの手掛かりになる。

## 深刻度の読み替え

グローバル側の一般定義を、このリポジトリでは次のように読む。

| 記号 | このリポジトリでの意味 |
|---|---|
| 💀 致死 | 起動・実行そのものが成立しない（プロセスが上がらない・永久ハング・先へ進めない） |
| 🔴 重大 | 動きはするが機能が壊れている、または**セキュリティ機構が無言で不発**（境界が立っていないのに成功に見える） |
| 🟡 軽微 | コード自体は正しく、実行環境・ビルド手順・設定の不一致など |

> **`🔴 重大` が最多である。** これは「サンドボックスが黙って効いていない」型が多いためで、
> 症状が出ないぶん発覚が遅れる。迷ったら**無言で不発かどうか**で切る。

**表記ゆれが実在する。** `🟡 中`・`🟡 軽微〜中` が使われた行がある。**新規は上の3語に揃える**
（中間が要るなら軽微側に寄せ、理由を症状欄に書く）。

## 状態の書き方

| 記号 | 使いどころ |
|---|---|
| `✅ 修正済み` | 既定。圧倒的多数はこれ |
| `🔍 調査中（<次の一手>）` | **括弧に次の一手を書く。** 「調査中」だけで置かない |
| `⚠️ 個別対応済み（<残っている一般化>）` | その場は塞いだが横展開が残っている |

**表記ゆれが実在する**（`✅ 解決済み`・`✅ 対応済み`）。**新規は `✅ 修正済み` に揃える。**

### 状態欄の括弧は「1行で読める要約」に留める

このリポジトリの `BUG_CATALOG.md` には、状態欄の括弧に**修正内容を1,000字超**書いた行がある。
`BUG_CATALOG.md` は**一覧インデックス**なので、詳細は `BUG-NNN.md` の「修正」節が持つ。
一覧の役割は「どれを開くか決められること」であって、開かずに済ませることではない。

## 相対リンクの実対応表（`docs/bugs/*.md` を基準）

バグ文書はリポジトリの中にあるので、相対リンクが正しく機能する（スキルとは違う）。

| リンク先 | 書き方 |
|---|---|
| クレートのソース | `../../crates/<crate>/src/xxx.rs` |
| 設計書・プラン | `../../plans/DESIGN-SANDBOX.md` / `../../plans/HANDOFF-<topic>.md` |
| 状態の正本 | `../STATUS.md` |
| フェーズ記録 | `../phases/foundation/Mxx-xxx.md` / `../phases/cognition/Mxx-xxx.md` |
| 解説ドキュメント | `../explanations/xxx.md` |
| 同じ bugs 内の他バグ | `BUG-003.md` |
| 図解 | `images/bug-NNN-xxx.svg` |

## 個別ファイルの項目表

グローバル側§3の構成に加え、このリポジトリでは冒頭の表に **`発覚` 行**を置く
（いつ・何をしていて気付いたか、どの残課題として記録されていたか）。

| 項目 | 値 |
|---|---|
| **ID** / **フェーズ** / **深刻度** / **状態** | 上記の規約どおり |
| **発覚** | `2026-MM-DD、<何をしていて気付いたか>。<それまでどう記録されていたか>` |

「それまでどう記録されていたか」（例: `docs/STATUS.md` の残課題#NN として原因未確定のまま
置かれていた）を書くと、**残課題として何か月も寝ていた**という事実が残る。これは
[[quality-improvement-loop]] が「構造で直すもの」を選ぶときの材料になる。

## 記録した後にやること

- [ ] `docs/bugs/BUG_CATALOG.md` に1行追記（ID・フェーズ・深刻度・症状一行・状態）
- [ ] 残課題を1つ解消したなら `docs/STATUS.md` から消す（残課題の正本はあちら）
- [ ] 設計の記述が実態と変わったなら、対応する `plans/DESIGN*.md` の該当節を**上書き**する
- [ ] 教訓が汎用なら、グローバルスキル [[bug-pattern-rules]] の `B-NN` へ実例を1行足す
      （**このリポジトリ名を添えて**。番号は他リポジトリと衝突する）

判断フローの正本は `docs/DOCUMENT-RULES.md`「新しい事実が出たときにどの文書を直すか」である。

## このスキルの育て方

このリポジトリのカタログで新しい表記ゆれ・新しい軸のフェーズ表記が出たら、ここへ1行足す。
**書式の話ならグローバル側**（[[bug-catalog-rules]]）へ足す——迷ったら「他のリポジトリでも
同じことが言えるか」で決める。言えるなら書式である。
