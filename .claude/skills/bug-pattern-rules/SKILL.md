# 方式から引くバグの型（このリポジトリ）

> **ルール本体の正本はグローバルスキル [[bug-pattern-rules]]。** `B-NN` の中身・
> 「変更の形」から引く索引・§B設計ゲート・カタログの育て方は、すべてそちらが持つ。
> **ここへ複製しない。** 本スキルが持つのは**方式の一覧と、その方式が招いた実例**だけで、
> 避け方は既存の `B-NN` を**指すだけ**である。

## なぜこの索引が要るのか

グローバル側の索引は**「変更の形」**（付与を書く・速くする・並行化する）で引く。
これは**これから書くコードの形**なので、**方式を選んだ時点では引けない**。

だが実際には、方式を選んだ瞬間に型の束が確定している。実測（バグ146件の時点）——**このリポジトリのバグ146件のうち
71件（半分）がACL／DACLに触れており、そのうち22件は自分で「これは○○と同型だ」と書いている**。
**同型だと気付いたうえで繰り返している**ので、気付きは機構ではない。

## いつ引くか

1. **設計で方式・機構・アルゴリズムを選ぶとき**（グローバル `plan-review-gates` の検問9から来る）
2. **下表の方式に触る実装へ着手するとき**（グローバル `bug-pattern-rules` の索引から来る）
3. **既存の方式を問い直すとき**（例: `plans/HANDOFF-FS-BOUNDARY-STATIC-ACE.md`）

引いたら、その方式の「招く型」を**1つずつ自分の変更に当てる**。当たった型の `B-NN` だけを
グローバル側で開く（全部読むものではない）。

## 方式1: 静的ACE事前配布 — 21件

**何を選んだことになるか**: 許可したい各オブジェクトのDACLへ、サンドボックスのSID宛のACEを
**事前に**書く。境界はACLそのもので、フックは境界にしない（D-01）。
定義の原文は [`plans/HANDOFF-FS-BOUNDARY-STATIC-ACE.md`](../../../plans/HANDOFF-FS-BOUNDARY-STATIC-ACE.md)。

**招く型**

| 型 | 避け方 |
|---|---|
| **配る費用がノード数に比例し、起動のたびに払う。** 高速経路を入れても、書込APIを差し替えた瞬間に無症状で無効化される | `B-38`（スキップの条件は「自分がその状態にした」か）・`B-30`（遅さは既に壊れている兆候） |
| **配る側だけが最適化され、剥がす側が取り残される。** 対称化しないと撤収だけが遅いまま残る | `B-02`（付与側に入れた最適化は撤収にも要る）・`B-01` |
| **継承ACEは素直に消えない。** 取り消しAPIが効かない・条件付きACEが1本あると永久に撤収できない・凍結が無関係なACEまで壊す | `B-25`（継承ACEは `REVOKE_ACCESS` では消えない・実効で検証する）・`B-26`（効く口は関数ごとに違う） |
| **「書いた」と「効いている」が別。** 1ノードも保護しないまま成功が返る／フラグが立たない／ラベルの綴りが不正でも通る | `B-09`〜`B-12`（無言失敗）・`B-25`（実効で検証する） |
| **配り終える前に窓が開く。** 伝播の最中だけ保護が外れる | `B-37`（不変条件は操作の途中でも成り立つか） |
| **境界を置いた先がACLを保持できるとは限らない。** measureせずに前提にすると境界がゼロになる | `B-29`（前提を1つ測る） |

**実例**: BUG-006・012・013・014・018・019・020・044・081・082・083・084・088・089・099・103・106・129・130・140・145

> **同じ型に3件目が付いている**（配る側だけ最適化＝081・082・140、無言の未実施＝084・088・145）。
> グローバル側の育て方が言うとおり、**3件目はレビュー頼みをやめて機構で強制する合図**である。

**測って決着している前提が1つある（蒸し返さないこと）。** 「宛先SIDを分けると許可の本数が増えて
重くなる」は**偽**である——同じ場所のACEを3本まで増やしても、**1回の書込にまとめれば時間は動かない**
（実測1.0倍±3%）。**ただし宛先SIDごとに配り直すと約2.9倍**になる。
つまり**この方式の費用は実装の書き方だけで決まる**ので、「費用が増えるから方式ごと変えたい」
という論法は使えない。数値は [`plans/mac-spike/RESULTS.md`](../../../plans/mac-spike/RESULTS.md) §S15、
経緯は [M12の追記（2026-08-30）](../../../docs/phases/foundation/M12-shell-isolation-tiers.md)。

## 方式2: 台帳と実体の二正本 — 13件

**何を選んだことになるか**: 「何を付けたか」を、記録（台帳ファイル）と実体（実DACL）の
**2つ**で持つ。撤収は記録を索引にして行う。

**招く型**

| 型 | 避け方 |
|---|---|
| **付けてから記録するまでの窓で落ちると、撤収経路の無い残骸になる。** 保険がプロセスの生存を前提にしていると、強制終了では走らない | `B-15`（記録は実体の完成後・失敗は巻き戻す）・`B-37` |
| **部分適用が記録されない。** 途中で失敗した付与が「無かったこと」にされる | `B-15`・`B-01` |
| **記録が消えて実体が残る**（逆も）。片方だけ消せる経路が1つでもあると、そこから恒久的な残骸が出る | `B-13`（正本を2つ持たない）・`B-14`（台帳で実体の存在を代替しない） |
| **索引の置き場を間違えると、撤収が無言で0件になる。** プロセス内の変数を索引にすると、別プロセスから見て常に空 | `B-13`・`B-11`（保険の発火件数を出す） |
| **記録が古いまま「検証済み」として通る。** 実体を作り直しても記録が追随しない | `B-14`・`B-08`（1経路の確認を網羅の証明にしない） |

**実例**: BUG-017・026・028・038・057・059・066・092・101・110・112・119・142

## 方式3: 昇格ヘルパー経由の書込 — 8件

**何を選んだことになるか**: 特権が要る書込を、別プロセス（特権分離ヘルパー）へ委譲する。
非特権の親が要求を組み、受信側が検証してから実行する。

**招く型**

| 型 | 避け方 |
|---|---|
| **経路が2本になり、片方だけが決定に追随する。** 宛先SIDを変えたのにヘルパー側だけ旧いまま、が繰り返し起きている | `B-06`（呼び出しを全部数えたか）・`B-04` |
| **委譲を忘れた経路は「常に失敗する」形で出る。** 付与を委譲して撤収を委譲しない、が対になる | `B-01`・`B-06` |
| **起動と通信の順序を取り違えると、承認後にフリーズする** | `B-31`（asyncで同期ブロッキングを呼ばない）・`B-23` |
| **昇格したプロセスが作ったものは、非特権側から触れない**（所有者が変わる）。**直すときは「`.harness/`へ書く昇格プロセス」を種類ごとに数える**——BUG-109は収集器の1経路として直され、同じ形が`harness-netfilterd`（D-90段4で塞いだ）とTier3のデーモン（BUG-170、未修正）に残っていた。非特権側が先に作る直し方は、**ファイル名を非特権側が知っているときしか使えない** | `B-15`・`B-06`・`P-01`〜（`docs/SECURITY-PRINCIPLES.md`） |

**実例**: BUG-010・015・016・061・093・098・109・170

## 方式4: フックによる透過性 — 11件

**何を選んだことになるか**: 子プロセスのAPIを差し替えて、見え方だけを変える。
**この方式には拘束的決定が付いている**——`D-01`「フックは境界にしない。境界はカーネル強制のOS隔離へ置く」。

**招く型**

| 型 | 避け方 | 実例 |
|---|---|---|
| **注入の失敗が「成功」と誤判定されると、透過性が無音で失われる。** しかも子孫世代まで伝播する | `B-09`〜`B-12`（無言失敗）・`B-25`（実効で検証する） | BUG-045・BUG-175 |
| **フックが受け取るのは意図であって結果ではない。** 本当の呼び出しの前に台帳・状態を変えると、失敗した操作が「起きた」と残る | `B-15`（記録は本当の結果の後。**Redirectorでは機構で強制済み**）・`B-14`（記録が在ることは中身が変わったことを意味しない） | BUG-048 F2・BUG-171・BUG-172 層1・BUG-174 |
| **行き先のパスを書き換えると、Windows は書き換えた後の場所で「そのファイルが在るか」を判定する。** 差分層には触ったものしか無いので、本物には在るファイルが「無い」に見える。問い合わせが拒否されたときに「無い」と読むと、同じ形が逆向きに出る | 下の「在るかで結果が変わる操作は、書き換える前に判定する」・`B-04`（入口ごとに違う世界を見せない） | BUG-172 層2・BUG-173・BUG-176・BUG-177・BUG-180（差分層そのものを読めない子では、差分層の中のものが全部「無い」に見え、変更前の中身を黙って返した） |
| **巻き戻し・後片付けが、他のハンドル・スレッドがまだ使っているものを消す** | `B-16`（片付け条件は「今誰も使っていないか」）・`B-26` | BUG-178・BUG-175 |
| **1度しか入らない置き場と、再試行できる初期化を組み合わせる** | `B-21`（書いたつもりの値で判断しない） | BUG-179 |

### 在るかで結果が変わる操作は、書き換える前に判定する

**規則**: ファイル操作の行き先のパスを書き換える仕組み（Redirector）では、「そのファイルが既に在るか」で
結果が変わる操作——上書きしない名前の変更・新規作成だけの open・フォルダの作成（mkdir）・存在の問い合わせ
（`Test-Path` 等）——を、パスを差分層の中へ書き換えて Windows へ渡す**前に**、Redirector が論理的な見え方
（ワークスペース∪差分層−論理削除）で判定する。論理的な見え方と Windows の答えが食い違うなら、Windows へは
渡さずに Redirector が答え（「既に在ります」等）を返す。**問い合わせが拒否されたら「無い」ではなく
「分からない」として扱う**——サンドボックスの中から見た本物は、ACL が許した範囲しか答えない。

- **探す**: パスを差分層へ書き換えた直後に本当の呼び出しへ渡している箇所のうち、結果が行き先の状態
  （在る・無い・種類・親フォルダの有無）で決まるもの。あわせて、本当の呼び出しの**前に**差分層へ
  「論理的には無いもの」（親フォルダ・元の写し）を作っている箇所。
- **なぜ**: Windows は書き換えた後の場所（差分層）しか見ない。上書きしない移動が、ワークスペースにだけ在る
  ファイルを黙って置き換えた（BUG-176）。逆向きに、本当の呼び出しの前に差分層へ親フォルダを作っていたので
  本物なら「パスが無い」で失敗する作成が成功し、その副作用が「mkdir が一度も通っていない」という別の欠陥を
  1か月以上隠した（BUG-177）。
- **確認**: 操作ごとに「論理的な見え方での答え」と「差分層で Windows が返す答え」を表にし、食い違う行を
  Redirector 自身が答える。表は `open_route` の分岐の試験（`decide_open_route`）と名前の変更の判定の試験
  （`rename_refusal`）が持っている。
- **実例**: BUG-176（上書きしない名前の変更）・BUG-177 層1・層2（親フォルダを先に作る／mkdir が素通し）・
  BUG-172 層2（論理的には削除済みのファイルの元の中身を写した）。
- **置き場の経緯**: 2026-09-28 にグローバルの `bug-pattern-rules` へ `B-39` として立てたが、2026-09-29 に
  ユーザーの判断でこのリポジトリの索引だけへ移した（実例はすべて Redirector のもので、他のプロジェクトで
  当てはまる例をまだ見ていないため）。

**実例**: BUG-045・BUG-048（F2）・BUG-171〜BUG-179

> **1件だった頃、この欄には「D-01が先回りして禁じたこと」しか並んでいなかった。** 2026-09-27〜28の
> 品質改善ループ4周目で、BUG-171の根（本当の結果を見る前に記録する）の残りをRedirector全体で数え直し、
> 11件になって型が5つ見えた。**どれも境界ではなく透過性の欠陥である**——壊れていたのは
> セッションの中の見え方と台帳で、読取専用のワークスペースはACLが守ったまま、本物が変わり得るのは
> 承認（`harness apply`）を通ったときだけだった。D-01が効いていることの裏付けでもある。
>
> **直す場所を透過層にするか、突き合わせる側にするか。** 透過層で直すと、呼び出し元への返り値——
> サンドボックスの中の見え方——まで変わり得る。BUG-174は、DLL側で記録を遅らせる案が単体テストでは
> 緑のまま、実機で`File.Move`が何も動いていないのに成功を返すようになって撤回し、一覧と承認の側で直した。
> **透過層の変更は、サンドボックスの中で測るしかない**（CoW行列・`cow-diagnostics`・gitの経路）。

## 方式5: 名前から導出する宛先SID — 4件

**何を選んだことになるか**: 許可の宛先となるSIDを、名前（固定名または秘密）から
決定論的に導出する。名前を知っていれば誰でも同じSIDを作れる。

**招く型**

| 型 | 避け方 |
|---|---|
| **宛先SIDを分けた／変えたのに、剥がす側と診断側が旧い宛先SIDを見ている** | `B-06`・`B-02` |
| **1つのSIDを共有すると、共有範囲の全部にその許可が効く。** 「セッション専有だから安全」は宛先の共有範囲とは別の話 | `B-13`・`P-01`〜 |
| **自分のものでないSIDを「自分のもの」と名乗って剥がし得る。** 分類器でSIDを推定すると起きる | `B-20`（判定関数が自分で正規化する）・`B-25`（完全一致で判定する） |
| **秘密から導出する場合、秘密を失うと二度と剥がせない。** 導出し直す設計にしてはいけない | `B-13`・`B-15` |

**実例**: BUG-055・058・097・105

**取り違えやすい語が1つある。** 「**秘密の粒度**」と「**宛先SIDの共有範囲**」は別物である——
秘密は導出鍵ごと（このリポジトリでは`(ワークスペース, 宣言パス, access級)`）に別だが、
共有範囲はワークスペース単位。**2026-08-28に実装と食い違っていることが判明して言い直した**ので、
この方式を説明するときは**どちらの話かを先に言う**（正本は
[`plans/DESIGN-MAC-DOMAIN.md`](../../../plans/DESIGN-MAC-DOMAIN.md) §22.2.0の確定節）。

**秘密を要求電文に載せてよいかは、実測で決着している。** 本番と同じ形のサンドボックスの子は、
本番が実際に開いている昇格ヘルパーの受付を**開けない**（3回とも同じ。素のユーザーは開けて
電文まで読めるので対照も成立）。**ただし受付の名前は秘密になっていない**（子から一覧が取れる）——
守っているのはACLだけである。

## 方式6: テストが実マシンの共有状態を触る — 8件

**何を選んだことになるか**: 実DACL・実台帳・実プロファイルを読み書きするテストを書く。
モックでは境界の実効を測れないので、この方式自体は避けられない。

**招く型**

| 型 | 避け方 |
|---|---|
| **テストが共有資源を純減させる。** 冪等スキップで付与がno-opになり、撤収だけが効くと、永続の許可が消える | `B-38`・`B-27`（後始末は製品側か） |
| **テストが製品の台帳を書き換える**（復旧用のバックアップごと） | `B-27`・`B-13` |
| **走っていないのに緑。** 前提のバイナリが隣に無いだけでSKIPし続ける | `B-12`（実行件数を見る）・`B-27`（歯があるか） |
| **作ったつもりの状態が作られていない。** 失敗が「製品の前提が偽」の顔で出るので、原因を取り違える | `B-27`・`B-35`（禁止側と許可側を対にする） |
| **スコープ変更に追随せず、長期間赤のまま放置される** | `B-12`・`B-06` |
| **後始末が失敗しても捨てるので、実マシンに残骸が積もる。** ガードのdocは「必ず消す」と名乗っている | `B-10`（外に残るものを消す操作の失敗は捨てない）・`B-27` |
| **一時資源の名前にPIDを使うと、前回の残骸と衝突する。** PIDは再利用されるので「自分専用の名前」にならない | `B-10`・`B-17`（生存・一意性をPIDで代用しない） |

**実例**: BUG-011・046・052・091・108・136・144・157

## 方式7: 生存・使用中の判定を代用する — 10件

**何を選んだことになるか**: 「まだ使われているか」「もう死んだか」を、PID・ファイルの存在・
常駐プロセスの生死・プロセス内の状態などで代用する。

**招く型**

| 型 | 避け方 |
|---|---|
| **「確認してから作る／消す」の間に窓が開く。** 識別子を先に決めて、その場で確保しないと二重に作られる | `B-18`（確認→作成を不可分に）・`B-17`（排他はOSオブジェクトへ） |
| **代用した指標が本当の使用中と一致しない。** 稼働中を撤収し得る／常駐が生きている限り永久に片付かない | `B-16`（片付け条件は参照カウント）・`B-29` |
| **排他の単位を取り違える。** プロセス内の変数・同一スレッドの再入・跨プロセスでない排他 | `B-17`・`B-05` |
| **外の世界に残るものを、プロセスの生存に頼って片付ける。** 強制終了では走らない | `B-15`・`B-16` |
| **登録の時点が未規定だと、登録前に動き出したものが「台帳に無い」として扱われる** | `B-18`・`B-37` |

**実例**: BUG-024・027・029・085・107・116・117・141・146・155

## 方式をまたいで出る1つの型 — 「経路を全部数えたか」

**7方式のうち5つに同じ型が顔を出す**（方式1の対称化・方式2の索引・方式3の2本目の経路・
方式5の追随漏れ・方式6のスコープ追随）。**どれも `B-06`（呼び出しを全部数えたか）である。**

**数え落としは「気付かない」形ではなく「3つだと思っていたら4つだった」形で出る。**
直近の実例3件（いずれも残課題#20の作業中、2026-08-27〜30）——

| 何を数えていたか | 実際 |
|---|---|
| 撤収の配線点は3つ | **4つ**。4つ目は実装中に見つかった |
| 分流が持ち帰った設計判断 | **5件がどこにも数えられていなかった**（別の分流の分だけ数えていた） |
| 差分層のcapability SIDを運ぶ経路 | 付与2経路は数えられていたが、**トークンへ積む3経路をどの文書も数えていなかった** |
| 子のトークンへ積む到達先の一覧（2026-09-29） | 数え直して3経路と書いた**後**に、常駐daemonが別ドメインで子を起こす4経路目が足され、そこにだけ差分層が無かった（BUG-180）。**数えた記録は、次に経路を足す人を止めない** |

**だから方式を問わず、「N箇所のうちN箇所」の形で文書に残す。** 数を書かずに
「全部直した」と書くと、次に読む人はそれを検算できない。
経緯は [M12の追記（2026-08-30）](../../../docs/phases/foundation/M12-shell-isolation-tiers.md)。

## この分類の作り方と、その限界

**分類は2つの機械的な材料から作った。**

1. **バグ自身が書いた「同型」の宣言**（22件が相手をBUG番号で名指ししている）
2. **表題**（残り49件。表題から方式が読めるものだけを割り当てた）

**限界を3つ挙げる。**

- **同型宣言をグラフとして連結成分に畳むと、無関係な筋が1つに混ざる。** 実際に13件の塊が
  できたが、中身は「記録と実体がずれる」「配る側だけ直る」「張ったと宣言して張っていない」
  「候補除外の不足」の**4つの別々の筋**だった。**ハブになるバグを経由して繋がるだけ**なので、
  連結成分をそのまま分類に使ってはいけない。**宣言の文そのもの**を読んで束ねること。
- **1件のバグは1つの方式にだけ載せてある**（件数を数えられるようにするため）。実際には
  複数の方式にまたがるものがある（例: BUG-142 は台帳の二正本でもあり、配る側だけ直る型でもある）。
- **ACL系以外の75件は分類していない。** 同じ方式に載るものが在るかは見ていない。

## 育て方

**新しいバグを記録したら、既存の方式のどれかに載るかを見る。**

- **載る**: その方式の「実例」へ番号を足す。**同じ型に3件目が付いたら、避け方を
  レビュー（`B-NN`）から機構（コンパイル時・実行時の検算）へ移す検討を始める。**
- **載らない**: 方式を1本足すか、「方式起因ではない」へ入れる。**どちらにも入れずに黙って
  落とさない**（この節が在る理由がそれである）。
- **`B-NN` はここで新設しない。** 既存で説明できない型が出たら、グローバル
  `bug-pattern-rules` の「このカタログの育て方」に従って採番する（**入口ではなく該当する
  群のファイルへ書く**、と同スキルが定めている）。
